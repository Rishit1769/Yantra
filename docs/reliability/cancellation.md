# Cancellation

Cancellation propagates from caller to runtime loop, provider request, tool task, workflow descendants, and (for subprocess-bound tools) the direct worker process. A pre-observed cancellation is checked before the operation task starts. Pending approval is revoked in a `finally` path; late provider responses cannot pass the cancellation recheck and dispatch boundary. Worker startup is shielded until it either fails or returns a process that can be terminated. During cancellation cleanup, the direct child is terminated, waited for a bounded grace period, killed if needed, and reaped; repeated cancellation does not abandon that cleanup. Concurrent capacity is released in `finally`.

Cancellation racing a completed worker follows asyncio task-completion ordering: if the execution task has already completed when cancellation is observed, its result is consumed; otherwise cancellation propagates after cleanup. This is local task ordering, not atomicity with external effects. Descendant processes are not managed. Synchronous in-process handlers delegated to a thread cannot be forcibly stopped.

Runtime performs bounded cleanup under a shielded cleanup deadline, records cancellation requested/acknowledged and unfinished children, and reaches CANCELLED only when its local state policy is satisfied. Shutdown drains or cancels according to configuration. Tests cover cancellation at every await boundary, during retries, and during persistence commit.
