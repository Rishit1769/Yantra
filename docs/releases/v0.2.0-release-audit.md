# YANTRA v0.2.0 Release-Readiness Audit

**Audit date:** 2026-10-12\
**Scope:** Python package and YANTRA-001/YANTRA-002 implementation\
**Audited revision:** working tree based on `main` at `92d51eb` (`test(opencode): preserve unknown Go tool capability gate`)\
**Decision:** **NO-GO for tagging or publishing v0.2.0 from this checkout.**

This is a release-readiness assessment, not release authorization. No tag was created, no artifact was published, and no paid provider inference was run. The report distinguishes verified local evidence from user-reported provider results and remaining decisions.

## Executive Summary

The package builds, installs from both wheel and source distribution in isolated Python 3.12 environments, and passes its 125-test suite on macOS with Python 3.12, 3.13, and 3.14. Ruff, formatting, Pyright, and the locked dependency audit pass after the dependency update recorded below.

The checkout is not a v0.2.0 release candidate: project and lock metadata still say `0.1.0`, the license is unresolved, and the repository explicitly has no release process. Windows is configured in GitHub Actions but has no verified run evidence. These are release gates, not claims that the local package build or tests failed.

## Audit Corrections

These in-scope corrections were made while preparing the report:

- `uv audit --locked` initially reported `PYSEC-2026-1845` / `CVE-2025-71176` for locked `pytest 8.4.2`, with a fix available in pytest `9.0.3`. The development constraints now require `pytest>=9.0.3,<10` and `pytest-asyncio>=1,<2`; the lock resolves to pytest `9.1.1` and pytest-asyncio `1.4.0`. The asyncio constraint had to move because pytest-asyncio through `0.26.0` constrains pytest to `<9`.
- The generic adapter is an OpenAI Chat Completions-compatible endpoint, not an arbitrary protocol adapter. README, provider, gateway, and API documentation now describe that boundary accurately.
- Removed the `Operating System :: OS Independent` classifier because Windows execution has not been verified.
- The HTTP User-Agent previously hardcoded `yantra/0.2.0` while package metadata and `__version__` were `0.1.0`. It now derives from the same package-version module as the public `__version__`, preventing an independent literal from drifting.
- `CHANGELOG.md` records these audit corrections under Unreleased.

## Package And Security Review

- The wheel contains the `yantra` runtime package and distribution metadata; the source distribution includes source, tests, documentation, `README.md`, and `pyproject.toml`. The artifacts identify as version `0.1.0` and contain no license metadata.
- `git ls-files` found no tracked `.env`, key, certificate, database, or build artifact; `.env.example` contains replacement placeholders, not credentials. A focused token/private-key pattern scan returned no matches in the scanned workspace files. A dedicated secret-scanning tool was not installed, so this is not a comprehensive secret-scan certification.
- `uv audit` was used for dependency advisories. It is not a full source-code security review or a substitute for a release SBOM/provenance process.
- Endpoint validation in `src/yantra/providers/http.py` checks scheme, host allowlists, literal IP classes, and loopback/private-network policy before constructing the HTTP client. It does not pin or re-check resolved IP addresses at connection time. No DNS-rebinding bypass was demonstrated in this audit; consider resolution-aware controls and enforce outbound network policy when endpoints can be influenced by untrusted input.
- The runtime, tool authorization/execution loop, durable persistence, and production support remain unimplemented or unverified as stated by the README and feature matrix. This audit does not support a production-readiness claim.

## Provider Evidence And Limitations

Provider protocol tests use mocked HTTP transports. User-reported OpenCode Go text and streaming completions are not independently reproduced or accompanied here by sanitized request IDs/logs, so they are not counted as audit-verified live evidence. OpenCode Go tool-call support for `deepseek-v4.1-flash` remains unknown and is correctly gated; other providers' live account/model access was not tested. No billable inference or live catalog request was run.

## Required Follow-Up

1. Resolve and apply the v0.2.0 version decision; rebuild and inspect artifacts after the metadata change.
2. Select and document the project license, including package metadata and license file.
3. Adopt and execute a release process covering provenance/integrity, supported configurations, changelog, rollback, and clean artifact installation.
4. Run the configured macOS and Windows GitHub Actions jobs against the exact release candidate and review results.
5. Decide whether the unresolved endpoint DNS-resolution risk needs mitigation before release; retain explicit network egress controls for deployments.
6. Keep provider support and live-compatibility claims scoped to evidence; do not infer tool support from wire-format compatibility.

## Audit Boundary

The working tree contained a pre-existing untracked `AGENTS.md`; it was not edited, staged, or included in the audit changes. Generated `dist/` files are ignored local build outputs and are not candidates for commit or publication.
