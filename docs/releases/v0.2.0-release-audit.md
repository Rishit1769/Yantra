## Security Assessment

### Credentials And Endpoint Trust

- Credentials resolve at adapter-call time from environment or optional OS keyring references. Raw credentials are not accepted as CLI arguments; redaction and error-handling tests pass. No production credentials were used.
- Built-in adapters configure fixed provider hostnames. Custom compatible endpoints require an explicit trusted-host allowlist. URL-embedded userinfo, query, and fragment data are rejected. Default HTTPX clients use TLS verification, `trust_env=False`, and redirects disabled.
- Applications can inject a custom `httpx.AsyncClient`. Such a client bypasses YANTRA's default transport policy; the caller owns DNS/IP validation, redirects, TLS, proxy, egress, and credential-forwarding safeguards. This is documented as a security boundary.

### DNS/SSRF Finding

The earlier audit identified that hostname allowlisting and literal-IP checks alone did not prevent an allowlisted DNS name from resolving to a private or special-use address. This was a concrete address-policy gap in the default transport. It is mitigated in the candidate as follows:

- The default transport resolves at each new TCP connection, filters results, and passes an allowed literal IP to the connector. HTTPX/httpcore retains the original request hostname for TLS SNI and certificate verification, avoiding a DNS check/connect race.
- Private and special-use results are rejected by default for remote hostnames. Mixed answers use only allowed addresses. Changed DNS answers are rechecked on later connections.
- Loopback hostnames/IPs remain loopback-only for local inference. Other explicitly trusted private-network endpoints remain possible only when `allow_private_network=True` is set on an adapter whose hostname passes the trust allowlist.
- Redirects remain disabled by default, preventing an upstream redirect from changing the target of a credential-bearing request.
- Seven deterministic tests cover default transport wiring, public/private DNS filtering and pinning, private DNS rejection, changed DNS answers, explicit private endpoints, loopback-only resolution, and hostname mismatch. They use fake resolver results and make no network requests.

**Preconditions and residual risk:** a malicious or compromised actor who can alter adapter configuration, trusted hosts, `allow_private_network`, credentials, or an injected HTTPX client can still direct requests to destinations they control. Explicit private-network permission is intentionally trusted. A custom client is outside the default DNS/redirect controls. No real DNS rebinding attempt or external infrastructure scan was performed. The default guard is coupled to HTTPX's current internal httpcore pool hook because HTTPX does not expose a public network-backend injection point; tests fail if expected backend wiring changes. Deployments should retain outbound firewall policy.

### Dependency And Secret Review

- `uv audit --locked` found no known dependency vulnerabilities in the audited 34-package set. This is dependency-advisory evidence, not a full source-code security certification.
- Wheel/sdist archive scans and a focused token/private-key pattern scan found no credential files or matches. A dedicated secret-scanning product was not available; this is not a comprehensive secret certification.
- No unresolved critical/high vulnerability was identified in this assessment. The custom-client/configuration trust boundary and transport implementation coupling remain residual risks for release-owner review.

## Public API Findings

- `yantra.__version__` is sourced from `src/yantra/_version.py`; Hatchling derives PEP 621 version metadata from that file. Runtime metadata equality is tested.
- `ModelProvider.complete` is the required async contract; streaming and catalog/credential methods are optional adapter capabilities. Provider registration is explicit and performs no network I/O; no provider is auto-registered by a new gateway.
- `ModelRequest`, `ModelResponse`, `ModelStreamEvent`, capability declarations, tool proposals, token usage, and typed provider errors are implemented and have contract/mock tests. An accepted tool proposal is not tool execution or authorization.
- Capability declarations remain deployment/model-specific. Unknown is not supported; gateway preflight fails closed for required undeclared capabilities.
- Reasoning remains provider-specific metadata/events and is not fabricated as visible text by response normalization or the smoke display. Usage is nullable/provider-reported; cost is an estimate, not a guaranteed billing cap.
- The generic endpoint is the tested OpenAI Chat Completions-compatible subset, not an arbitrary protocol or full OpenAI API implementation.
- No CLI `--version` was added. Version is exposed through `yantra.__version__` and distribution metadata.
- The API is pre-1.0; `0.2.0` is not a stable compatibility promise. No YANTRA-003 agent loop or production execution system is claimed.

## Known Limitations

- Local verification covers macOS only. Ubuntu and Windows have no executed evidence; optional Windows Credential Locker integration is not exercised by the mock keyring tests.
- PostgreSQL backup/restore/init shell scripts are Bash/POSIX-oriented; native PowerShell support is not established.
- The default transport uses a guarded httpcore backend through HTTPX's private pool field. The wiring is covered by a test and fails closed if the expected backend is absent, but HTTPX/httpcore upgrades require compatibility review and CI.
- User-reported live OpenCode Go evidence was not rerun. All other provider/model behaviors remain mock-verified or unknown according to the matrix.
- No production SLOs, benchmarks, live provider matrix, or production security certification are claimed.
